Takeaways

  • AgenticTool calling holds up. On 150 BFCL v3 tasks the 2-bit models score 86.7% and 88.7% vs 82.7% for Q5. That gap is within noise at n=150, so read it as "no loss", which matches Saluki's own model card. Q5 drops most of its points on irrelevance detection (calling a tool when none fits).
  • KnowledgeThis is where the bits go. ThaiExam 70.6% → 59.9% → 52.0%, A-Level 66.9% → 52.0% → 38.6%, MMLU-Pro 58.6% → 53.6% → 45.0%. The order follows bpw exactly.
  • ReasoningGSM8K, HumanEval and a small thinking-on MMLU-Pro math set are flat across all three (within 1–2 items).
  • FormatAsked to "reply with only the letter", Bonsai complied 41% of the time (Q5 99%, Saluki 96%). It tends to explain first, which matters for pipelines that parse terse output.
  • Speed2.0–2.4× faster decode on one GPU, but prefill is roughly equal (~760–880 tok/s at 30k tokens), so on long agent prompts the gain is in generation only. Thinking traces run ~35% longer on the 2-bit models.

Follow-up · 2026-10-13

Same size class, four quantizers

Qwen publishes no GGUF of Qwen3.8-27B, only BF16 and FP8 safetensors. So the Unsloth file above was run against three other quantizers' builds of the same weights in the same 17–21 GB class. Harness and profile were identical: 2 GPUs, 131072 ctx, q8_0 KV.

  • Speed is not. The Unsloth file has the slowest prefill. The NVFP4 build (mostly Blackwell-native FP4, Q5_K/Q6_K on sensitive tensors, imatrix from agent sessions) gets +53% prefill and +17% decode at 30k, with 3.6 GB less VRAM on an sm_120 card.

MTP roughly doubles decode, but it costs prefill because the draft head also runs over the prompt. With a 30k prompt and a short answer, NVFP4 is faster without MTP. Acceptance was measured at temp 0. At temp 1.0 earlier runs saw 64–79%, so expect less in real sampling. For long-prompt agentic coding on this rig, NVFP4 + MTP is the pick: same quality, the fastest prefill among the MTP options, and about 4 GB more headroom.

Method

  • Same harness, same items, same order for all three: OpenAI-compatible /v1/chat/completions, temperature 0, seed 0, enable_thinking: false except the thinking-on set. Each model runs with its normal production profile (131072 ctx, q8_0 KV, FA on).
  • BFCL v3 (Berkeley Function Calling Leaderboard), 150 tasks: simple 40, multiple 30, parallel 30, parallel_multiple 20, irrelevance 30. Native tool calls checked AST-style against the official possible-answer files (name, required args, allowed values, no extra args). It follows the leaderboard's rules, but it isn't the official checker.
  • MMLU-Pro: 10 questions per category × 14 categories (up to 10 options). ThaiExam (typhoon-ai/thai_exam): all 354 O-NET, TGAT and A-Level test questions.
  • Multiple choice is grammar-constrained. A GBNF grammar allows exactly one option letter, so every model answers directly. Without it, Bonsai ignored "letter only" 59% of the time, and the explanation worked as chain-of-thought (85/140 on MMLU-Pro, above Q5's 82). Q5 scored the same with or without the grammar, so the constraint doesn't hurt models that comply.
  • GSM8K: 60 random test problems, CoT allowed, answer after ####. HumanEval: 50 problems, generated code executed against the official tests with a 15 s timeout.
  • Thinking on: 6 MMLU-Pro math questions, 12k-token budget. Too small to rank anything; it's there for reasoning length and time.
  • Noise. These are small samples. Treat 1–3 item differences as noise. The Thai and MMLU-Pro gaps are well beyond that, the BFCL gap is borderline.

PSA for Bonsai users: prism-b10772 regression

The newest PrismML llama.cpp release at the time (prism-b10772-e8fd209, Windows CUDA 13.3) broke this setup. After about five requests the model starts emitting ////// and stays broken until restart, even for "What is the capital of France?". A freshly started server answers fine, so a one-question smoke test won't catch it. Same flags and the same request sequence on prism-b10754: no problem. This matches PrismML issue #342. The likely cause is the short-query MMA flash-attention change for quantized V (#189), and a fix is proposed in #353. If you run Bonsai with a quantized KV cache and FA, stay on b10754 or test with 10+ requests before upgrading.
